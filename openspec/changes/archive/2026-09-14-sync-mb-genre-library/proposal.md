# MusicBrainz 风格库全量同步

## 背景

手动给专辑分配风格时，编辑框的候选只能来自本地 `genre` 表，而该表**当前只包含「已经被某张专辑用过」的风格**（数据补全写入的 MB 风格 + 历史手动标签），不存在「全量词表」的概念。

叠加 `manual-genre-edit` 的既有约束「不支持创建新风格」（UI 对输入库中没有的标签按回车无任何处理），结果是：想给专辑打一个 MB 上有、但本地尚无专辑使用的风格（如 `shoegaze`），用户只能手动改数据库插入一行，再重启应用让 `album:filters` 重新返回新列表。

MusicBrainz 官方维护了一份受控风格词表（对应 https://musicbrainz.org/genres 文档页所列），通过 WS/2 `GET /ws/2/genre/all` 可分页获取，**实测全量 2201 个**。把它一次性同步进本地库，即可从根本上消除这个手工步骤。

注：数据层其实早已具备建标签的能力（`setAlbumGenres` 有 `INSERT OR IGNORE INTO genre` 兜底），卡点纯粹在「本地没有这个词表」。

## 目标

- 菜单「数据 → 同步 MusicBrainz 风格库」一键把 MB 全量风格写入本地 `genre` 表（23 页请求，约半分钟，带进度条）。
- **纯增量写入，绝不破坏已有数据**（本需求的硬约束）：
  - 只 INSERT 本地缺失的风格行；已有行只在 `mb_genre_id` 为空时补写该列，**不改 name、不改 id**；
  - **绝不 DELETE `genre` 任何行，绝不触碰 `album_genre`** —— 已有专辑↔风格的映射零风险。
- 同步后无需重启应用：编辑框候选立即包含新同步的风格。
- 幂等可重跑：第二次同步新增数为 0；MB 词表变化后重跑即收敛。
- 工具栏风格筛选建议只列「至少关联一张专辑」的风格，避免筛出必然为空的全量风格。

## 非目标

- **不放开自由创建标签**：编辑框仍只能在本地风格库中挑选，MB 官方词表是标签的唯一来源（维持 `manual-genre-edit` 的「不支持创建新风格」约束）。
- 不做定时/自动同步，保持手动触发（与项目「手动同步」的总体原则一致）。
- 不抓取 https://musicbrainz.org/genres 的 HTML 页面（文档页无分页接口），只用官方 WS/2 接口。
- 不同步 `disambiguation` 说明文本与使用量计数，不做风格层级、别名、翻译。
- 不改动风格统计（`genre-stats`）语义：仍只统计有关联专辑的风格。
- 不改动数据补全写入风格的既有行为（`setAlbumGenres` 的 `INSERT OR IGNORE` 兜底保留）。

## 方案概述

详见 design.md。核心决策：

- **数据源**：WS/2 `GET /ws/2/genre/all?fmt=json&limit=100&offset=N`，响应的 `genre-count` 给出总数；复用 `musicbrainz-api` 已公开的 `restGet()`，自动走现有 1 req/s 限流。
- **限流韧性**：实测 23 页里撞到 7 次 503，而库内建重试的间隔固定 500ms 不够用，故同步服务在页级别再加一层指数退避重试；单页最终失败则中止并保留已写入部分（幂等，重跑即续）。
- **写入策略**：每页一个事务批量落库；同步前把现有 `genre` 行读进内存建 `lower(name) → id` 索引（用 JS 的 `toLowerCase` 而非 SQL 的 `lower()`，后者只处理 ASCII，会漏掉 `afoxé` 这类名称），大小写不敏感去重，避免手工建的 `Rock` 与 MB 的 `rock` 并存。
- **来源标记**：`genre` 新增可空列 `mb_genre_id`（MB 风格 UUID），用于标记来源并支撑将来按 UUID 检测改名/合并。
- **候选拆分**：`album:filters` 改为只返回在用风格（工具栏筛选用），新增 `genre:library` 返回全量风格（编辑框用）；编辑框候选上限 50 条 + 「还有 N 个匹配」提示行。
