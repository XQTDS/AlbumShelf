# 唱片墙快速跳转性能优化

## 背景

专辑量大时（当前约 2,454 张，同步上限 10,000），快速跳转到视图偏底部位置会卡顿。典型复现：搜索定位到一张位于底部的专辑 → 选中 → 清空搜索框 → 卡顿。核实代码后确认三处根因：

1. 跳转定位路径 `fetchAlbumsAndScrollTo` 用 `while` 循环**逐页顺序加载**直到目标专辑出现——底部专辑约 62 轮 IPC + 62 次递增重渲染（累计 O(n²) diff）。
2. 清空搜索框只加载第 1 页（40 张）并回到顶部，选中专辑被移出列表、详情面板收起；此后拖动自定义滚动进度条只能到达已加载内容末尾，哨兵 IntersectionObserver 一页页加载，用户需反复拖动。
3. 已加载卡片全部留在 DOM（全量约 15,000 节点 + 2,454 张封面），每次追加整列表重新 diff；单卡模板函数未缓存；封面图急切加载。

## 目标

- 跳转定位（清除筛选/搜索/随机选/播放条封面点击）改为**一次 IPC 拉取完整结果集**并定位，替代逐页循环
- 深拖滚动进度条到已加载内容末尾时，一次拉全量并按相同比例继续滚动
- 清空搜索框后若存在选中专辑，**定位并保持选中**（与清除流派/艺术家筛选的现有行为一致）
- 全量结果集可负担：`content-visibility` 跳过离屏渲染、封面懒加载、`v-memo` 免重复渲染

## 非目标

- **不做虚拟滚动**（沿用既有分页 + 无限滚动机制；此前在 2026-04-16-scroll-list-with-progress-bar 与 2026-08-17-album-grid-view 的设计文档中已两次明确"未来可升级虚拟滚动"，专辑量逼近 10k 上限时再评估）
- 不取消分页：冷启动、搜索输入、新增筛选仍按页加载（表格 20/页、网格 40/页）
- 不做 `album:position` 定位查询 IPC（方案 C，见 design.md 方案选型）
- 不做封面缓存淘汰/预下载等缓存策略工作

## 方案选型

- **方案 A（采用）**：`album:list` 新增 `fetchAll` 模式，跳转与深拖路径单次拉全量；配合 `content-visibility` / 懒加载 / `v-memo` 使全量渲染负担可控。改动集中、风险低。
- **方案 B（否决，留待后续）**：手写虚拟滚动（窗口化渲染）。彻底解决任意数据量 DOM 压力，但需同时改造网格/表格两套视图、进度条与定位逻辑，在 4,396 行 App.vue 中风险高；当前数据量下 A 已可解决卡顿。
- **方案 C（否决）**：`album:position` COUNT 定位查询 + 目标页 ± 邻页稀疏窗口 + 双向哨兵。复杂度最高，SQLite OFFSET 大页码退化，收益不及一次 ~1.5MB 本地 IPC 传输。
